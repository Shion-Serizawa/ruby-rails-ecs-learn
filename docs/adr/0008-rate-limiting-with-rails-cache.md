# ADR-0008: レート制限は Rails.cache で数え、メールは実送信数で数える

- 状態: 採用
- 日付: 2026-11-05

## 背景

ログイン・新規登録・パスワードリセット・インポート・エクスポートを、総当たりや大量アクセスから守りたい。
特にパスワードリセットはメールを送るので、他人へのメール爆撃や大量送信 (SES の評判低下) に悪用されうる。

## 決定

- リクエスト単位の制限は Rails 8 標準の `rate_limit` を使う (IP 単位、ユーザー単位など)
- カウンタは `Rails.cache` に置く。本番は Solid Cache (DB) なので ECS の複数タスクで共有される
- パスワードリセットメールは `PasswordResetThrottle` で **実際に送った通数** を数える (宛先ごと 1時間3通、全体 1時間100通)
- 制限にかかっても画面の応答は変えない (アドレスの登録有無を推測させない)

## 検討した他の案

| 案 | 採用しなかった理由 |
| --- | --- |
| すべて `rate_limit` (リクエスト数) で数える | 存在しないアドレス宛ての連打で全体の上限を使い切られ、正規ユーザーのリセットまで止まる |
| Rack::Attack | 実績はあるが、Rails 8 標準の `rate_limit` で足りる |
| WAF のレートベースルールだけ | アプリの文脈 (宛先ユーザーごと等) で数えられない。CloudFront を置く場合は併用を検討 |

## 結果

- 良い: 追加のミドルウェアなしで、タスク数に関係なく正しく数えられる
- 悪い: キャッシュが使えないとき (`:null_store`) は制限が効かない。`PasswordResetThrottle` は安全側 (送らない) に倒す
- 注意: CloudFront を前段に置くと IP 単位の制限が機能しなくなる。詳細は [deployment.md](../deployment.md)
